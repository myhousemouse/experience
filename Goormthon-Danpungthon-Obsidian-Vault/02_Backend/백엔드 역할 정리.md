# 백엔드 역할 정리

## 기술 스택

- Java 17
- Spring Boot 3.3.5
- Spring Web, Spring Security, OAuth2 Client
- Spring Data JPA
- MySQL 8.0
- Swagger/OpenAPI
- Flyway
- Docker Compose

## 확인된 직접 기여 범위

GitHub 계정 `myhousemouse` 커밋 기준으로 다음 백엔드 기능 구현 근거가 확인된다.

기능명세서 기준으로는 메인 페이지의 `버스 운행 현황`, `버스 신청 현황`, `버스 신청하기` 흐름을 중심으로 작업했다. API 문서에서 체크 표시가 있는 항목은 사용자가 직접 구현한 기능으로 분류한다.

### 버스 신청/신청 현황

- `/applications` 버스 신청 생성 API
- `/applications/summary` 지역/날짜별 신청 현황 요약 API
- 정원 50명 기준 신청 수, 잔여 인원, 충족률 계산
- 신청 데이터와 지역 데이터 간 관계 처리

### 정류장 조회

- `/stops/nearest` 사용자 좌표 기반 가장 가까운 정류장 조회
- `/stops/{stopId}` 정류장 상세 모달 조회
- Haversine 거리 계산
- 정류장 좌표, 지역명, ETA, 남은 정차 시간 응답
- Swagger 예시 응답 정리

### 지역/노선 검색

- `/regions/search` 전국 지역 계층 검색
- `/regions/{regionId}/service` 지역과 날짜 기준 운행 코스/정류장 조회
- `regions.json` 기반 광역/기초 지역 계층 데이터 처리
- 평일 요일 매핑 후 코스와 정류장 목록 반환

### 실시간 버스 정보

- `/courses/{courseId}/live` 코스별 실시간 버스 현황 조회
- 버스의 정차/이동/오프라인 상태 판정
- 현재/다음 정류장 progress 계산
- 정류장별 ETA와 남은 정차 시간 응답
- `/bus-live/ingest` 실시간 데이터 ingest 확장 지점 작성

## 어려웠던 기술 문제

가장 어려웠던 지점은 기획상 “이동 도서관 버스가 우리 지역에 어떻게 오고, 지금 어디에 있으며, 언제 도착하는가”를 백엔드 데이터와 API로 변환하는 일이었다.

- 신청 데이터는 지역/일자별 수요로 집계해야 했다.
- 사용자의 주소/좌표는 최근접 정류장과 매핑되어야 했다.
- 정류장 수요는 코스와 방문 순서로 이어져야 했다.
- 지도 화면은 현재/다음 정류장, ETA, 남은 정차 시간을 한 번에 요구했다.

해결은 기능을 한 번에 구현하기보다 `신청 현황`, `정류장 조회`, `지역/노선 조회`, `실시간 버스 상태`로 API를 쪼개는 방식으로 진행했다. 자세한 정리는 [[02_Backend/어려웠던 기술 문제와 해결 과정]]에 분리했다.

## 협업 관점의 역할

- 프론트에서 필요한 모달/지도 화면의 응답 구조를 API 스펙으로 정리
- Swagger 예시 응답을 추가해 프론트 연동 부담을 낮춤
- Docker Compose로 MySQL 개발 환경을 통일
- ERD와 API 문서를 바탕으로 도메인을 `application`, `region`, `bus`, `user`로 분리

## 결과 상태

- 해커톤 결과: 완주
- 백엔드 상태: API와 산출 로직 구현 및 백엔드 측 동작 확인
- 프론트 연동 상태: 시간 부족으로 최종 화면 연동 미완
- 배포 상태: 별도 배포 링크 없음, GitHub와 Notion API 문서로 근거 관리
