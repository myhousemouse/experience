## 문제

단순 CRUD보다 어려웠던 부분은 지도 기반 이동 도서관 서비스를 백엔드 데이터 구조와 API 응답으로 풀어내는 것이었다.

서비스는 사용자가 “우리 지역에도 도서관 버스가 와줬으면 좋겠다”는 수요를 신청하면, 그 수요를 지역/일자 단위로 집계하고, 정류장과 코스, 실시간 운행 정보로 이어줘야 했다. 즉 신청 데이터, 지역 데이터, 정류장 좌표, 버스 코스, 실시간 상태가 한 흐름으로 연결되어야 했다.

## 어려웠던 이유

- 기획 화면은 지도/모달 중심이었지만, 백엔드는 이를 정류장, 코스, 버스 상태, ETA, 정차 시간 같은 데이터로 쪼개야 했다.
- 사용자의 위치와 정류장 좌표를 비교해 가장 가까운 정류장을 찾아야 했다.
- 지역 검색 결과가 단순 텍스트 검색이 아니라, 해당 지역의 운행 코스와 정류장 목록으로 이어져야 했다.
- 실시간 버스 정보는 “현재 정차 중인지, 이동 중인지, 다음 정류장이 어디인지”를 상태값으로 판단해야 했다.
- 해커톤 일정상 프론트와 충분히 연동하며 수정할 시간이 부족했기 때문에, API 문서와 예시 응답을 더 명확히 해야 했다.

## 해결 과정

### 1. 기능을 API 단위로 분해

메인 페이지 기능을 한 번에 처리하지 않고 다음 API 단위로 나눴다.

- 신청 현황: `/applications/summary`
- 버스 신청: `/applications`
- 가장 가까운 정류장: `/stops/nearest`
- 정류장 상세 모달: `/stops/{stopId}`
- 지역/노선 조회: `/regions/search`, `/regions/{regionId}/service`
- 실시간 버스 상태: `/courses/{courseId}/live`

이렇게 분리하면서 프론트 화면의 모달, 지도, 신청 현황 UI가 각각 어떤 응답을 필요로 하는지 명확해졌다.

### 2. 도메인 모델을 먼저 정리

`Users`, `Regions`, `Stops`, `Course`, `CourseStops`, `Buses`, `BusLive`, `Applications`, `CapacityPlan`을 중심으로 ERD를 정리했다.

특히 `Applications`는 수요 집계의 기준이 되고, `Stops`와 `CourseStops`는 지도/노선 화면의 기준이 되며, `BusLive`는 실시간 운행 상태의 기준이 된다.

### 3. 위치 기반 정류장 조회 구현

사용자 좌표와 정류장 좌표 사이의 거리를 계산해 가장 가까운 정류장을 찾도록 했다. 코드 기준으로는 Haversine 거리 계산을 사용했고, 응답에는 정류장 좌표, 지역명, 거리, ETA, 남은 정차 시간을 함께 담았다.

관련 구현:

- `NearestStopController`
- `NearestStopService`
- `StopsRepository`
- 커밋: `d3f3edc`, `ada0cd5`, `6a7ed82`

### 4. 지역/노선 조회 구현

지역 검색은 단순 검색 결과에서 끝나지 않고, 사용자가 선택한 지역과 날짜에 따라 운행 코스와 정류장 목록을 반환하도록 구성했다.

관련 구현:

- `RegionsController`
- `RegionsService`
- `RegionHierarchyProvider`
- `regions.json`
- 커밋: `3c41832`, `d983048`

### 5. 균형 클러스터링으로 방문 순서와 ETA 산출 방향 정리

가장 감이 안 잡혔던 부분은 “신청자가 여러 지역에 흩어져 있을 때 버스가 어떤 순서로 방문해야 하는가”였다. 단순히 가까운 순서대로만 정렬하면 특정 코스에 정류장이 몰리거나, 어떤 요일은 너무 길고 어떤 요일은 너무 짧아지는 문제가 생길 수 있었다. 그래서 먼저 수요를 비슷한 규모의 코스로 나누고, 그 안에서 방문 순서를 정하는 방식으로 접근했다.

#### 문제를 나눈 방식

1. 신청자 주소를 좌표 또는 정류장 기준 위치로 변환한다.
2. 각 신청자를 가장 가까운 정류장에 매핑한다.
3. 정류장별 신청 수요를 집계한다.
4. 정류장을 여러 코스로 나눈다.
5. 각 코스 안에서 방문 순서를 정한다.
6. 고정 체류 시간과 이동 시간을 기준으로 ETA를 계산한다.

#### 균형 클러스터링을 쓴 이유

일반적인 거리 기반 클러스터링만 쓰면 가까운 정류장끼리 묶을 수는 있지만, 각 코스의 수요량이나 정류장 수가 균등하다는 보장은 없다. 이동 도서관은 하루에 처리할 수 있는 정류장 수와 이용 가능 시간이 제한되어 있으므로, 단순히 “가까운 곳끼리 묶기”보다 “비슷한 부담의 코스로 나누기”가 중요했다.

그래서 코스를 만들 때 다음 기준을 함께 고려했다.

- 정류장 간 거리
- 정류장별 신청자 수
- 하루에 방문 가능한 정류장 수
- 코스별 총 체류 시간
- 코스별 예상 이동 시간

면접에서는 이 부분을 “거리만 최소화한 것이 아니라, 특정 요일/코스에 수요가 몰리지 않도록 균형 있게 분배하려 했다”고 설명하면 좋다.

#### 방문 순서 산출 방식

균형 클러스터링으로 코스가 나뉜 뒤에는 각 코스 내부에서 방문 순서를 정해야 했다. 이때 완전한 최적해를 구하려고 하면 해커톤 범위에 비해 너무 무거워지기 때문에, 다음처럼 휴리스틱하게 접근했다.

- 코스 내 첫 정류장은 지역 중심 또는 가장 대표성이 높은 정류장으로 둔다.
- 이후에는 현재 정류장에서 가장 가까운 다음 정류장을 선택한다.
- 이미 방문한 정류장은 제외한다.
- 정류장 수가 많아질 경우, 이동 거리 합이 과도하게 커지는 순서는 제외한다.

즉 TSP를 완전 탐색으로 푼 것이 아니라, 해커톤 MVP에 맞춰 가까운 정류장부터 이어 붙이는 방식으로 방문 순서를 산출하는 방향을 잡았다. 이 방식은 최적해는 아니지만 구현 난이도와 설명 가능성, 제한된 시간 안의 완성도를 고려하면 현실적인 선택이었다.

#### ETA 계산 방식

ETA는 복잡한 실시간 교통량까지 반영하기보다는 MVP 기준으로 고정값을 두고 계산했다.

- 코스 시작 시간: 09:00
- 기본 정차 시간: 30분
- 정류장 간 이동 시간: 30분
- 동일 정류장 또는 수요가 많은 정류장은 정차 시간을 늘리는 방식으로 처리

예를 들면 첫 정류장 도착 시간이 09:00이고 정차 시간이 30분, 다음 정류장까지 이동 시간이 30분이면 두 번째 정류장의 ETA는 10:00이 된다. 이 계산을 정류장 순서대로 누적하면 각 정류장별 도착 시간과 마감 시간을 만들 수 있다.

#### 이 접근의 장점

- 해커톤 시간 안에 구현 가능한 수준으로 문제를 단순화했다.
- 지도 UI가 필요로 하는 정류장 순서와 ETA를 만들 수 있었다.
- 신청 데이터가 늘어나도 코스별 수요를 재분배하는 방향으로 확장할 수 있다.
- 이후 실제 서비스로 발전한다면 교통 API, 운영 시간, 차량 수, 도서관 인력 등을 추가 조건으로 넣어 고도화할 수 있다.

#### 이 접근의 한계

- 실제 도로 교통량이나 도로망 기반 최단 경로를 완전히 반영하지는 못했다.
- 최적 경로 알고리즘을 엄밀하게 구현한 것이 아니라 MVP 수준의 산출 로직에 가깝다.
- 프론트 연동이 완료되지 않아 지도 화면에서 코스/ETA가 최종 검증되지는 못했다.

면접에서는 이 한계를 숨기기보다 “해커톤에서는 구현 가능한 수준의 산출 로직으로 풀었고, 실제 서비스라면 교통 API와 제약조건을 추가해 고도화할 수 있다”고 말하는 편이 정확하다.

### 6. 실시간 버스 상태 응답 구성

지도 화면에서 필요한 정보는 “버스가 정차 중인지, 이동 중인지, 다음 정류장이 어디인지, ETA가 얼마인지”였다. 이를 위해 `BusLive`의 최신 상태를 기준으로 `STOPPED`, `IN_SERVICE`, `OFFLINE`을 판단하고, 현재/다음 정류장 순서를 계산했다.

관련 구현:

- `BusLiveController`
- `BusLiveService`
- `BusLiveResponseDto`
- 커밋: `1ffb0c3`

## 결과

- 백엔드 API와 산출 로직은 구현했고, 백엔드 측에서는 동작 확인이 가능했다.
- 기능명세서의 메인 페이지 흐름 중 `버스 운행 현황`, `버스 신청 현황`, `버스 신청하기`에 필요한 핵심 API를 만들었다.
- 다만 해커톤 시간 제약으로 프론트엔드와 최종 연동하지 못해, 앱 화면에서 백엔드 기능을 완전히 검증하지는 못했다.

## 면접에서 말할 표현

> 가장 어려웠던 부분은 지도 기반 서비스를 백엔드 API로 쪼개는 일이었습니다. 기획상으로는 “버스가 우리 지역에 오고, 지금 어디에 있는지 보여준다”는 흐름이었지만, 백엔드에서는 신청 수요, 지역, 정류장 좌표, 코스, 실시간 상태를 각각 모델링해야 했습니다. 그래서 메인 페이지 기능을 신청 현황, 정류장 조회, 지역/노선 조회, 실시간 버스 상태 API로 분리했고, 좌표 기반 거리 계산과 코스별 상태 응답을 구현했습니다. 최종적으로 백엔드 API와 산출 로직은 동작했지만, 해커톤 시간상 프론트 연동까지 완료하지 못한 점은 한계였습니다.

## 균형 클러스터링 면접 답변

> 방문 순서와 ETA를 짤 때 가장 어려웠던 점은 단순히 가까운 정류장만 묶으면 코스별 부담이 불균형해질 수 있다는 점이었습니다. 그래서 먼저 신청자 주소를 최근접 정류장에 매핑하고, 정류장별 수요를 집계한 뒤, 정류장 수와 신청자 수가 한 코스에 과도하게 몰리지 않도록 균형 클러스터링 관점으로 코스를 나눴습니다. 그 다음 각 코스 내부에서는 현재 정류장에서 가까운 다음 정류장을 선택하는 휴리스틱으로 방문 순서를 만들고, 시작 시간 9시, 기본 정차 30분, 이동 30분 같은 MVP 기준값을 누적해 ETA를 계산했습니다. 실제 교통량까지 반영한 최적화는 아니지만, 해커톤 범위에서는 지도 화면에 필요한 코스 순서와 도착 시간을 산출할 수 있는 현실적인 방식으로 문제를 단순화했습니다.
