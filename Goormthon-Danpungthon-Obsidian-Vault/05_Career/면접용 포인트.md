# 면접용 포인트

## 한 줄 경험

해커톤에서 백엔드로 참여해 청소년 수요 기반 이동 도서관 서비스의 신청, 지역/노선 검색, 정류장 조회, 실시간 버스 상태 API와 산출 로직을 구현하고 프론트 연동을 위한 응답 스펙과 개발 환경을 정리했다.

## PM/기획 직무로 말할 때

- 지역 간 교육/문화 접근성 격차라는 문제를 서비스 기능으로 변환한 경험
- 신청-운영 확정-정류장/노선 확인-실시간 위치 확인으로 사용자 흐름을 구조화한 경험
- 해커톤 시간 제약 안에서 MVP와 확장 기능을 분리한 경험
- 프론트가 실제로 필요한 응답 단위를 기준으로 API를 정리한 경험

## 백엔드/개발 직무로 말할 때

- Spring Boot, JPA, MySQL 기반으로 도메인별 API를 구현한 경험
- 좌표 기반 가까운 정류장 조회와 거리 계산을 구현한 경험
- 코스/정류장/실시간 버스 상태를 조합해 지도 UI용 API를 만든 경험
- Swagger 예시 응답, Notion API 문서, Docker Compose를 통해 협업 생산성을 높인 경험
- 최종 화면 연동은 미완이었지만, 백엔드 API와 산출 로직은 독립적으로 구현/동작 확인한 경험

## AX/데이터 직무로 말할 때

- 사용자 신청 데이터를 기반으로 수요를 계산하고 운영 확정 판단에 연결하는 구조를 설계한 경험
- 향후 신청자 거주지 기반 클러스터링, 일정 최적화, 맞춤 추천으로 확장 가능한 데이터 구조를 고려한 경험

## STAR 초안

- Situation: 도서관/문화 시설 접근성이 낮은 지역 청소년을 위한 이동 도서관 서비스 아이디어를 해커톤에서 구현해야 했다.
- Task: 백엔드 파트로서 메인 페이지에 필요한 신청 현황, 지역/노선, 정류장, 실시간 버스 API를 구현하고 프론트가 사용할 응답 스펙을 맞춰야 했다.
- Action: Spring Boot/JPA/MySQL 기반으로 도메인을 분리하고, 좌표 기반 정류장 조회, 지역 계층 검색, 코스별 실시간 상태 API를 구현했다. Swagger 예시와 Notion API 문서를 병행해 프론트 연동 기준을 명확히 했다.
- Result: 지도/모달/신청 현황 화면에 필요한 핵심 API와 산출 로직을 구현해 백엔드 측 동작을 확인했다. 다만 해커톤 시간 제약으로 프론트 연동까지 완료하지 못해 화면 시연은 제한적이었다. 프로젝트는 완주했다.

## 어려웠던 기술 문제

가장 어려웠던 점은 지도 기반 이동 도서관 서비스를 백엔드 API로 분해하는 일이었다. 신청 수요, 지역, 정류장 좌표, 코스, 실시간 버스 상태가 모두 연결되어야 했기 때문에 단순 CRUD보다 데이터 관계와 응답 구조 설계가 중요했다.

해결 과정은 [[02_Backend/어려웠던 기술 문제와 해결 과정]]에 정리했다.

면접용 핵심 문장:

> 기획상으로는 “버스가 우리 지역에 오고 지금 어디에 있는지 보여준다”는 흐름이었지만, 백엔드에서는 신청 수요, 지역, 정류장 좌표, 코스, 실시간 상태를 각각 모델링해야 했습니다. 그래서 기능을 신청 현황, 정류장 조회, 지역/노선 조회, 실시간 버스 상태 API로 나누고, 좌표 기반 거리 계산과 코스별 상태 응답을 구현했습니다.

균형 클러스터링 설명:

> 방문 순서와 ETA를 짤 때는 단순히 가까운 정류장만 묶으면 코스별 부담이 불균형해질 수 있다고 봤습니다. 그래서 신청자 주소를 최근접 정류장에 매핑하고 정류장별 수요를 집계한 뒤, 정류장 수와 신청자 수가 특정 코스에 몰리지 않도록 균형 클러스터링 관점으로 코스를 나눴습니다. 이후 코스 내부에서는 가까운 정류장부터 이어 붙이는 휴리스틱으로 방문 순서를 만들고, 시작 시간·정차 시간·이동 시간을 누적해 ETA를 계산했습니다.

## 솔직하게 말해야 할 한계

- 프론트엔드와 백엔드가 완전히 연동된 최종 앱 화면은 확인하지 못했다.
- 배포 링크나 운영 Swagger는 없다.
- 따라서 “서비스 전체를 배포했다”가 아니라 “백엔드 API와 산출 로직을 구현했고, 해커톤을 완주했다”로 말하는 것이 정확하다.
