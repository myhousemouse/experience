# 개인 기여 정리

## 2026-10-14 최신 확인 — 새 자소서 작성 시 우선 적용

출처: SK브로드밴드 자소서 작성 대화의 사용자 설명·정정. 개인 진술이며 독립 인증 아님. 아래 내용과 기존 본문이 다르면 아래 최신 범위를 적용한다.

- 백오피스 관심과 경영정보학 복수전공을 배경으로 PM·고객사 소통 플랫폼 기획에 참여했다. 기획 담당이며 팀 전체 개발을 단독 수행한 것으로 쓰지 않는다.
- PM 2명과 IT 외주 경험 고객 50명을 조사해 분산된 소통 채널과 IT 용어 이해·질문의 어려움을 파악했다. 조사 방식·응답 비율은 미확인이다.
- 처음부터 고객사 한 곳 이상이 실제 소통에 사용하는 것을 목표로 삼았다. 회의록 보관함은 파편화된 기록 추적, 문장·단어별 질문은 이해하지 못한 부분의 질문 편의를 위해 설계했다. 자동 요약·문장별 질문은 정규 기간에 팀이 구현했고 이후 고객사 사용 단계에서도 사용됐다고 확인했다.
- 약 한 달의 정규 프로젝트·시험기간으로 실제 도입까지 못했으나 팀은 기업 프로젝트 대상을 받았다. 대표에게 추가 개발 한 달을 제안했고 후속 약 4주 AX 교육형 인턴으로 출퇴근했다. 추가 개발과 인턴을 하나의 한 달로 합치지 않는다.
- 팀 플랫폼과 현업 흐름이 맞지 않았다. 기존에는 없던 프로젝트별 단계 설정이 추가 관리 부담이었다. 단계 설정을 빼고 홈에 Figma·개발 서버를 임베드해 결과물을 바로 보는 방안을 제안했다. 사내 대시보드 연동은 점진적 확대 방향이다. 제안과 실제 반영 범위를 구분한다.
- 서로 다른 고객사 두 곳의 시범 사용을 확인했고 본인 계약 종료 후에도 정식 사용 중이라고 설명했다. 본인 계약 종료를 고객사 계약 종료로 해석하지 않는다. 현재 활성 고객 수는 별도 미확인이다.
- PM은 기존 5개 초과 채널을 사용 시 1~2개로 줄일 수 있다고 예상했다. 실제 감소·절감률로 바꾸지 않는다.
- 팀원 8명이라는 최신 설명과 기존 5명 기록이 다르므로 전체 인원은 확인 전 빼고 쓴다. 베타 시점도 이전 6월 초·AX 후반 설명 차이가 있어 정확한 날짜를 확정하지 않는다. 개인 기여율 미확인.

재사용 에피소드: **LT-Q1 실제 사용 목표를 수상 이후 도입까지 이어간 경험**. 상황·최초 목표→양측 조사·MVP→기간 제약→연장 제안·현업 흐름 수정→고객사 두 곳 시범 사용. 수상과 실사용은 다른 결과다.

## 한 줄 요약

실제 기업 과제에서 문제 정의를 바탕으로 MVP를 도출하고, 개발 협업을 거쳐 실제 기업이 사용하는 파트너 플랫폼까지 연결한 기획 경험이다.

## 프로젝트 맥락

큐시즘 IT경영학회에서 리트머스와 진행한 산학협력 기업 프로젝트다. 리트머스가 제시한 과제를 바탕으로 고객사 전용 프로젝트 관리 플랫폼을 만들었고, 1차는 2026.02.08 ~ 2026.03.16에 진행했고, 팀이 추가 진행을 제안해 2026.04.16까지 연장했다.

기업 과제 이후에는 대표님 제안으로 2026년 4월부터 5월까지 주 5일 출근하는 [[리트머스 AX 교육형 인턴]]으로 이어졌다.

## 직접 기여

### WorkOS 기반 진입 설계

회원가입-로그인 로직이 WorkOS 보안 절차를 거쳐야 해서 진입 설계가 복잡했다. 로그인, 인증, 회원가입 절차를 각각 나누고, 엣지케이스를 시각화해 화면 흐름과 개발 전달 기준을 정리했다.

로그인/파트너 페이지 개발 링크: https://partners-page-sooty.vercel.app/

### 회의기록 기능

회의기록 기능을 설계했다. 와이어프레임, 요구사항명세서, 기능명세서 등 개발 전달에 필요한 산출물을 작성했고, 고객사와 PM이 같은 회의 정보를 서로 다른 권한과 목적에서 볼 수 있도록 구조화했다.

### 문서함 기능

문서함 기능을 설계했다. 외주 프로젝트에서 기획서, IA, 계약서, 견적서, 디자인 레퍼런스, 기능명세서 같은 산출물이 흩어지는 문제를 줄이기 위해 폴더 구조와 문서 확인 흐름을 잡았다.

### QA 기능

QA 기능은 설계와 디자인까지 완료했지만, 기업 미팅을 진행하면서 필요성이 낮다고 판단되어 최종 개발 범위에서 제외됐다. 이 경험은 기능을 많이 넣는 것보다 기업 요구와 실제 사용 맥락에 맞춰 MVP 범위를 줄이는 판단으로 정리할 수 있다.

### 추가 프로젝트 GUI

추가 프로젝트 연장 과정에서 생긴 기능 GUI에 약 50% 정도 기여했다.

## 판단 기준

- 대표님 피드백을 가장 우선했다.
- 회의록끼리 충돌하면 최신 회의록을 더 정확한 기준으로 봤다.
- 최종 GUI는 전체 화면 개발 완료 기준으로 판단했다.
- Figma 최종 GUI의 빨간불, 초록불, 파란불 순서를 기능 중요도로 봤다.
- 빈값이거나 없는 화면은 미팅 중 필요하지 않다고 결론이 나 작업하지 않은 범위로 해석했다.

## 면접에서 강조할 포인트

- 실제 기업과의 과제를 통해 문제 정의에서 개발 완료까지 이어간 경험
- 리서치와 기업 피드백을 바탕으로 MVP 범위를 조정한 경험
- 로그인/인증/회원가입처럼 개발 복잡도가 높은 플로우를 시각화해 협업한 경험
- 회의기록, 문서함, QA처럼 기능별 요구사항을 설계하고 개발 전달 문서로 정리한 경험
- 필요 없는 기능을 제외하는 판단까지 포함한 MVP 기획 경험
- 결과물이 실제 기업에서 사용 중이라는 점
- 기업 과제 이후 인턴으로 이어져 내부 대시보드 AX 개선과 기능 추가를 수행한 점
