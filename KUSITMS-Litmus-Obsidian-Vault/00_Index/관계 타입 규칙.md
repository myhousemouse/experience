# 관계 타입 규칙

태그: #ontology #relationship #index

## 목적

리트머스 vault에서 문서 링크가 단순 참조가 아니라 어떤 의미로 연결되는지 표현하기 위한 규칙이다.

## 관계 타입

- 과제: 리트머스가 제시한 기업 요구와 수행 범위
- 근거: 유저 리서치, PM 인터뷰, 기업 미팅, UT 결과
- 검증: MAZE UT, 내부 QA, 기업 피드백으로 확인한 내용
- 인사이트: 근거와 검증을 해석해 도출한 문제, 니즈, 사용성 시사점
- 결정: 기능 범위, 우선순위, 화면 구조, 개발 범위에 대한 판단
- 반영: 결정이나 인사이트가 옮겨간 화면, 기능명세, 발표, 개발
- 기준: 충돌 시 우선해서 따라야 하는 문서나 원본
- 구현: 개발 공통, FE/BE, API, 배포 플랫폼과의 연결
- 협업: 내부 회의, 기업 미팅, 파트 간 전달과 조율
- 회고: 취준/면접에서 경험으로 재구성할 수 있는 판단과 배움
- 실무확장: 기업 과제 이후 인턴, AX 개선, 내부 대시보드 개선으로 이어진 경험

## 우선순위

1. 기업 미팅에서 확인한 대표님 요구사항
2. 최신 회의록
3. [[최종 GUI]]와 실제 개발/배포 화면
4. [[최종보고서]], [[최종 발표]]
5. [[MAZE UT결과]], [[UT 기록]]
6. [[유저 리서치 방향성]], [[PM 인터뷰]]
7. 오래된 내부 회의록

기업 프로젝트이므로 내부 논의와 기업 요구사항이 충돌하면 대표님 피드백을 우선한다. 회의록끼리 충돌하면 최신 회의록을 더 정확한 기준으로 본다. 최종 GUI는 전체 화면이 개발 완료된 상태이므로, 화면/기능 범위를 판단할 때 실제 구현 기준으로 사용한다.

Figma 최종 GUI의 기능 우선순위는 빨간불, 초록불, 파란불 순서로 본다. 빈값이거나 없는 화면은 기업 미팅 중 필요하지 않다고 결론이 나 작업하지 않은 범위로 해석한다.

## 핵심 관계

```text
리트머스 과제
-> 유저 리서치 방향성 / PM 인터뷰
-> 1차 기획 회의 / 기디 회의 / 전체 회의
-> UT 시나리오_v2 최종
-> MAZE UT결과
-> 최종보고서 / 최종 GUI / 최종 발표
-> 추가작업 기획
-> 대표님 요구사항 정리 4-8
-> 개인 기여 정리
-> 개발 공통 / 배포 플랫폼
-> 리트머스 AX 교육형 인턴
```
