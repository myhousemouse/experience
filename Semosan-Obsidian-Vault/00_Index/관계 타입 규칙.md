# 관계 타입 규칙

태그: #ontology #relationship #index

## 목적

세모산 Obsidian Vault에서 문서 링크가 단순한 참조가 아니라, 어떤 의미로 연결되는지 일관되게 표현하기 위한 규칙이다.

## 관계 타입

- 근거: 리서치, 설문, 인터뷰, 관찰에서 나온 원천 자료
- 검증: UT, 현장 테스트, QA, Maze, 설문 결과로 확인한 내용
- 인사이트: 근거와 검증을 해석해서 얻은 문제, 니즈, 시사점
- 결정: 기획 방향성, 우선순위, 서비스 정체성처럼 확정하거나 기준으로 삼은 내용
- 반영: 결정이나 인사이트가 옮겨간 기능 명세, 발표자료, 화면, 플로우
- 기준: 충돌이 있을 때 우선해서 따라야 하는 문서나 원본
- 디자인: 최종 GUI, 디자인 시스템, Figma 화면과의 연결
- 구현: API, 프론트엔드, 백엔드 구현 기준과의 연결
- 데이터: ERD, DB, 객체 모델, 데이터 구조와의 연결
- 소통: 팀 간 핸드오프, 개발자/디자이너 협업을 위한 연결
- 후속작업: 아직 남은 개선, 확인, 보완 대상

## 우선순위

1. 최종 GUI/Figma 화면
2. 발표 PPT와 발표대본에 정리된 최종 방향성
3. 기능 명세서
4. UT 인사이트와 리서치 원문

기능 명세서와 최종 GUI가 충돌하면 최종 GUI/Figma 화면을 더 신뢰한다. 기능 명세서는 개발 전달용 기준이지만, 애자일하게 바뀐 내용은 최종 디자인 화면에 더 정확히 반영되어 있을 수 있다.

## 핵심 흐름

```text
유저리서치
-> UT 테스트 가이드
-> UT 인사이트 결과
-> UT 이후 기획 고민
-> 데모데이 발표자료 / 발표대본
-> 최종 GUI / 디자인 시스템
-> API 명세서 / ERD
```
