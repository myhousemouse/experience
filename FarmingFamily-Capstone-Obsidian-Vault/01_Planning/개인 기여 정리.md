# 개인 기여 정리

태그: #contribution #planning #python #chatbot

## 역할 요약

사용자는 이 프로젝트에서 기획과 Python 기반 챗봇 시스템 구현을 함께 수행했다. 개인 페이지에서 LangChain, LangGraph, RAG, FastAPI, FAISS, 임베딩, Tavily 웹검색 등을 따로 공부하며 챗봇 구조를 실험했고, 이를 팀 협업 페이지의 서비스 흐름과 연결했다.

## 역할 범위

- 기획: 100%
- 발표: 100%
- 보고서: 100%
- 개발: 시스템 구조도 정리 및 챗봇 시스템 구현 100%
- 디자인: 약 50%

기획, 발표, 보고서는 전부 사용자가 주도했다. 개발에서는 전체 서비스 개발을 모두 맡은 것은 아니지만, 시스템 구조도 정리와 핵심 기능인 챗봇 시스템 구현을 주도했다. 디자인도 약 50% 수준으로 기여했다.

## 핵심 기여

- 서비스 기획과 시연 흐름 정리
- 최종 발표자료와 최종 결과보고서 작성
- 식물 병해충 진단 이후 AI 상담으로 이어지는 사용자 흐름 설계
- 챗봇 시스템 구현 방식 학습 및 코드 실험
- direct answer, 전문 DB 검색, 웹 검색을 분기하는 LangGraph 기반 라우팅 구조 설계
- PDF/농업 데이터 기반 벡터 DB 구축 실험
- FastAPI로 `/api/chat` 엔드포인트 구성
- GitHub `gardendoctor_ai-server` 저장소 기준 챗봇 서버 초기 구현
- LangGraph ReAct agent, FAISS 벡터 DB, 농진청 API 연동, 농업 전문 fallback 시스템 구현
- 챗봇 세션/메시지 저장, 조회, 삭제 API 개선
- 챗봇 히스토리 저장/조회/검색/삭제 구조 검토
- Swagger API 문서 배포 확인
- 최종 발표/보고서 산출 흐름 정리

## 챗봇 구현에 도전한 이유

사용자는 기획 역할이었지만 챗봇 시스템이 서비스의 핵심 기능이라고 판단해 직접 개발에 도전했다. 병해충 진단만으로 끝나는 서비스라면 사용자가 추가 질문을 할 때 신뢰도 높은 후속 상담을 제공하기 어렵다고 보았다.

경쟁 서비스를 분석하면서 병해충 진단 결과를 보여준 뒤 사용 흐름이 끝나는 문제를 발견했다. 사용자가 진단 이후 재배법이나 날씨를 이어서 묻도록 만드는 AI 챗봇을 차별화 지점으로 정했다.

핵심 판단:

- 사용자는 병해충 진단 이후 추가적인 2차 질문을 할 가능성이 높다.
- 단순 GPT API 호출만으로는 농업/병해충 상담의 신뢰성을 확보하기 어렵다.
- 전문 DB, 일반 GPT 답변, 웹검색처럼 서로 다른 응답 경로를 질문 유형에 따라 붙여야 UX적으로 더 신뢰할 수 있다.
- 챗봇은 부가 기능이 아니라 병해충 진단 이후의 사용 경험을 완성하는 핵심 기능이다.

데스크 리서치와 인터뷰로 사용자의 병해충 대응 과정을 조사하면서, 진단 결과를 확인한 뒤에도 방제 방법과 재배 관리에 관한 후속 질문이 이어진다는 점에 주목했다. 이 관찰을 바탕으로 예상 질문을 정리하고, 일반 답변·전문 데이터 검색·웹 검색 중 어떤 경로가 적합한지를 나누어 챗봇 구조에 반영했다.
- 실제 사용자는 기획 단계에서 예상한 질문 목록만 사용하지 않고, 목록에 없는 내용을 묻거나 같은 의도를 다른 표현으로 질문한다.
- 따라서 질문을 단순 목록으로 매칭하는 방식이 아니라 농업 전문 정보, 실시간 정보, 일반 질문의 세 유형으로 분류하고 응답 경로를 달리해야 한다.

## 문제 상황과 해결

처음 배우는 챗봇 시스템 구현이라 LangChain, LangGraph, RAG, 임베딩, FastAPI 구조가 서툴렀다. 피드백, 서적, AI 독학을 기반으로 구현 방식을 계속 학습했고, 결국 질문 유형별로 다른 응답 경로를 붙이는 챗봇 시스템을 구현했다.

문제:

- 챗봇 시스템 구현 경험 부족
- 단순 GPT API의 일반 답변 한계
- 병해충/농업 전문 질의에 대한 신뢰성 확보 필요
- 최신 날씨/지역 정보처럼 실시간 정보가 필요한 엣지케이스 존재
- 예상 목록 밖의 질문과 표현이 다른 질문을 같은 의도로 처리해야 하는 문제

해결:

- 전문 DB 기반 RAG 구조를 학습
- 웹검색 API를 붙여 실시간 정보 대응 가능성 확보
- 일반 질문, 전문 DB 질문, 실시간 정보 질문을 분기하는 구조 설계
- FastAPI 엔드포인트로 챗봇을 서비스 기능에 연결

검증:

- 질문 의도가 불분명한 경우의 응답 확인
- 전문 DB 검색 결과가 부족하거나 관련 문서가 없는 경우 확인
- 일반 답변, 전문 DB와 웹 검색 사이의 라우팅 결과 확인
- 진단 이후 방제 방법, 관리 방법과 현재 날씨를 묻는 후속 질문 확인
- 답변 경로에 따라 정보 출처와 상세 수준이 달라지는 상황 점검

- CORS 설정과 requirements 정리로 프론트 연동 및 실행 환경 보강
- SQLite 기반 ChatSession/ChatMessage 테이블을 추가해 대화 세션 저장 구조 구현

## 면접용 포인트

- 기획에서 끝난 것이 아니라 Python/FastAPI 기반 챗봇 구현까지 직접 확장한 경험
- RAG, 웹검색, 일반 GPT 답변을 질문 유형별로 분기하는 구조를 설계한 경험
- 제한된 토큰/비용 문제 때문에 OpenAI 임베딩에서 Hugging Face 임베딩으로 전환을 검토한 경험
- 농업 도메인 데이터와 실시간 정보가 섞이는 서비스 특성을 고려해 전문 DB와 웹검색을 함께 사용하는 구조를 만든 경험
- 팀 협업 산출물과 개인 기술 학습을 연결해 시연 가능한 결과로 만든 경험
- 기획자 포지션에서는 사용자 흐름과 핵심 기능 정의를, 개발자 포지션에서는 FastAPI/RAG/LangGraph 구현을, AX 포지션에서는 AI 도구와 에이전트형 시스템 설계를 강조할 수 있는 경험

## 성과와 평가

기획서에 머물던 기능을 실제로 시연할 수 있는 API와 챗봇으로 완성했다. 최종 피드백에서는 진단 이후 상담으로 이어지는 서비스 흐름과 설명의 설득력이 좋다는 평가를 받았다. 수상이나 정량 성과보다, 처음 배우는 기술을 독학해 핵심 기능 구현까지 연결하고 프로젝트를 마무리한 것에 의의를 둔다.
