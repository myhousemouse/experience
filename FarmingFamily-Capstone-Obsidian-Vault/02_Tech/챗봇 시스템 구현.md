## 구현 목표

식물/농업 관련 질문에 대해 일반 LLM 답변, 전문 DB 기반 답변, 실시간 웹검색 답변을 구분해 제공하는 챗봇 시스템을 구현하는 것이 목표였다.

사용자는 기획 역할이었지만 챗봇을 핵심 기능으로 보고 직접 구현에 도전했다. 병해충 진단 후 사용자가 추가 질문을 할 가능성이 높고, 그 질문에 대한 답변 품질이 서비스 신뢰도를 좌우한다고 판단했기 때문이다.

GitHub `KSEB-AI-3/gardendoctor_ai-server` 기준으로는 `myhousemouse` 계정의 초기 커밋에서 FastAPI 챗봇 서버, LangGraph ReAct 구조, FAISS 벡터 DB, 농진청 API 연동, 농업 전문 fallback 시스템이 확인된다.

## 초기 접근

초기에는 ChatGPT API로 답변을 구현했다. 하지만 일반적인 답변 수준에 머물러 병해충 진단이나 농업 전문 상담에는 한계가 있었다.

단순 GPT API만 붙이면 빠르게 구현할 수는 있지만, 다음 엣지케이스에 약하다고 판단했다.

- 병해충/작물 관련 전문 지식이 필요한 질문
- 현재 날씨나 위치 기반 정보처럼 실시간성이 필요한 질문
- 전문 DB에 있는 작물과 없는 작물이 섞이는 질문
- 진단 결과 이후 사용자가 방제 방법, 관리 방법, 재배 조건을 이어서 묻는 질문

## 수동 라우터 구조

LangGraph 기반 수동 라우터 방식으로 3단계 플로우를 설계했다.

1. `direct_answer`: GPT-3.5 직접 답변
2. `knowledge_db`: 전문 PDF DB 검색 및 요약
3. `web_search`: Tavily 웹검색 및 GPT 요약

분기 기준:

- 직접 답변이 가능하면 그대로 반환
- 답변에 `모르겠습니다`, `잘 모르겠` 등이 포함되면 전문 DB 검색으로 이동
- 전문 DB에 관련 문서가 없거나 너무 짧으면 웹검색으로 이동

## ReAct Agent 구조

이후에는 ReAct agent 방식으로 확장했다. 사용자의 질의를 보고 에이전트가 RAG, GPT API, 웹검색 중 적절한 도구를 자동 선택하는 구조다.

핵심 개념:

- `@tool`로 기능을 도구화
- 도구의 docstring을 기반으로 LLM이 적절한 도구를 선택
- PromptTemplate에 도구 설명과 도구 이름을 주입
- ReAct 방식으로 reasoning과 action을 반복

## 임베딩 전환

OpenAI 임베딩 모델은 토큰/비용 제한 때문에 많은 DB를 넣기 어렵다고 판단했다. 이후 Hugging Face `sentence-transformers/all-MiniLM-L6-v2` 기반 임베딩으로 전환해 무료 요금제에서도 더 많은 데이터를 다룰 수 있도록 검토했다.

## 전문 DB 구성

전문 DB에는 농작물 병해충 발생정보 API 데이터와 작물 농업기술길잡이 책자를 넣는 방향으로 설계했다.

문서 처리 흐름:

1. PDF 및 API 데이터 로드
2. 텍스트 추출
3. 문서 청크 분할
4. Hugging Face 임베딩 생성
5. FAISS 벡터스토어 저장
6. Retriever로 관련 문서 검색

## 테스트 시나리오

- 당근 관련 질문: 전문 DB PDF 사용
- 딸기 관련 질문: 전문 DB에 없으면 GPT-3.5로 일반 답변
- 수원시 날씨: 웹검색 후 GPT-3.5로 요약 답변

## 사용자 흐름 및 예외 상황 검증

데스크 리서치와 인터뷰에서 병해충 진단 이후에도 대처 방법을 묻는 후속 질문이 이어진다는 점을 확인했다. 이에 예상 질문을 정리하고 단순 성공 응답뿐 아니라 다음 예외 상황을 반복해서 점검했다.

- 질문 의도가 불분명해 라우팅 경로를 정하기 어려운 경우
- 전문 DB에 관련 작물이나 문서가 없는 경우
- 검색된 문서가 짧거나 답변 근거로 사용하기 부족한 경우
- 현재 날씨와 지역 정보처럼 웹 검색이 필요한 경우
- 진단 결과 이후 방제 방법과 재배 조건을 연속해서 묻는 경우
- 일반 답변, 전문 DB와 웹 검색에서 답변 출처와 상세 수준이 달라지는 경우

이 검증을 통해 기획 단계에서 자연스러워 보이던 `진단 -> 추가 상담` 흐름도 실제 구현에서는 데이터 유무, 질문 유형과 실시간성에 따라 분기 기준이 필요하다는 점을 확인했다. 챗봇을 직접 구현하고 테스트한 경험은 사용자 흐름의 단절과 기술적 한계를 동시에 발견한 사례로 정리한다.

## GitHub 기준 구현 범위

- `chat_server.py`: FastAPI 서버, `/api/chat` 엔드포인트, CORS 설정, 챗봇 세션 API
- `langgraph_agent_react.py`: LangGraph/ReAct 기반 agent 실행, direct answer/knowledge DB/web search 도구 구성
- `embeddings/build_vector_db.py`: PDF 및 농진청 API 데이터 로드, 청크 분할, Hugging Face 임베딩, FAISS 저장
- `database.py`: ChatSession, ChatMessage 테이블 추가
- `models.py`: ChatRequest, ChatSessionResponse, ChatSessionWithMessages, ChatMessage 모델 추가
- `requirements.txt`: FastAPI, LangChain, LangGraph, FAISS, sentence-transformers, Tavily 등 의존성 정리

## 구현 과정의 어려움

처음 배우는 시스템이어서 LangChain, LangGraph, RAG, 임베딩, FastAPI 연결이 모두 낯설었다. 피드백, 서적, AI 독학을 기반으로 구조를 이해하고, 단순 API 호출에서 질문 유형별 라우팅 구조로 발전시켰다.

## UX 관점의 판단

챗봇은 단순 부가 기능이 아니라 병해충 진단 이후의 사용자 경험을 이어주는 핵심 접점이다. 사용자가 사진 진단 결과를 받은 뒤 `왜 이런 병이 생겼는지`, `지금 무엇을 해야 하는지`, `오늘 날씨 기준으로 관리가 필요한지`를 물을 수 있으므로, 응답 경로도 하나로 고정하면 안 된다고 판단했다.

그래서 질문 유형별로 다른 API/DB/검색 경로를 붙여 신뢰성을 높이는 방향으로 설계했다.

## 한계와 개선 포인트

- 웹서치만 사용할 경우 답변이 빈약할 수 있었다.
- GPT-3.5는 자세하게 답변하지만 병해충 진단 수준의 전문성이 부족했다.
- 전문 DB가 없거나 청크 품질이 낮으면 답변 품질이 떨어질 수 있다.
- 추후 사용자 위치 정보를 함께 전달하면 실시간 날씨/지역 정보 상담이 더 자연스러워진다.
