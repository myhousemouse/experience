## 읽어봤을 때의 평가

이 프로젝트는 취업 준비에 넣을 만하다. 다만 "개발 프로젝트를 완전히 구현했다"보다 "실제 회사 요구사항을 분석해 DB 구조, SQLite CRUD SQL, 응용 화면 흐름으로 설계한 프로젝트"로 말하는 편이 더 정확하다.

강점은 수업 프로젝트임에도 실제 고객사 맥락이 있고, 종이/수기 기반 업무를 데이터베이스로 구조화했다는 점이다. 개발 직무로 말할 때는 SQLite, CRUD SQL, 물리 설계, ERD, 데이터 모델링을 중심에 두면 좋고, 기획/PM 직무로 말할 때는 요구사항 분석, 업무 프로세스 이해, 팀 역할 분배를 중심에 두면 좋다.

## 면접용 한 줄

데이터베이스 시스템 수업에서 실제 건설 회사 대표님과 대면미팅을 진행하며 수기 기반 자재/협력업체 관리 문제를 분석했고, 프로젝트-자재-주문-협력업체 데이터를 관리하는 SQLite 기반 DB 구조와 CRUD SQL 작성에 참여했습니다.

## 개발 직무로 말할 때

- 실제 업무 요구사항을 테이블 구조와 관계로 변환한 경험
- ERD와 물리 설계를 통해 데이터 무결성과 조회 흐름을 고민한 경험
- SQLite로 기본 CRUD SQL을 전반적으로 작성한 경험
- 팀원들과 수기로 관계 차수와 제약조건을 검토한 경험
- UI 흐름과 DB 구조가 함께 맞아야 업무 시스템이 작동한다는 점을 배운 경험

## 기획/PM 직무로 말할 때

- 고객사의 기존 업무 방식과 불편을 파악해 문제를 정의한 경험
- 협력업체, 자재, 주문, 프로젝트라는 업무 객체를 구조화한 경험
- 팀원별 강점을 고려해 역할을 나누고 협업 방식을 정리한 경험
- 개발 산출물과 보고서 산출물이 같은 방향을 보도록 조율한 경험

## AX/업무개선 관점으로 말할 때

- 수기/종이 기반 업무를 데이터 기반 업무 흐름으로 전환하려 한 경험
- 현업 사용자의 컴퓨터 활용 수준을 고려해 쉬운 UI와 조회 흐름을 설계한 경험
- 초기 회사에 맞는 최소한의 DBMS 구조를 제안하고, 이후 확장 가능성을 고려한 경험

## 추천 포지셔닝

내가 보기에는 이 프로젝트는 `개발 60 + 기획/업무분석 40` 정도로 잡는 게 좋다. 순수 백엔드 구현 프로젝트처럼 말하기보다는, 실제 회사의 수기 업무를 분석하고 SQLite 기반 DB 스키마와 CRUD 흐름으로 구조화한 프로젝트로 말하는 편이 설득력이 높다.

개발 직무에서는 "요구사항을 데이터 모델과 SQL로 바꿔본 경험"으로 쓰고, PM/기획 직무에서는 "현업의 비정형 업무를 구조화해 개발 가능한 요구사항으로 만든 경험"으로 쓰면 된다.

## 추가로 기억해보면 좋은 질문

1. 고객사에서 받은 실제 자료는 뭐였어? 견적서, 도면, 자재 목록, 협력업체 목록 같은 게 있었는지 기억나?
2. CRUD SQL 중 대표로 보여줄 수 있는 예시가 있어? 예: 협력업체 조회, 자재 주문 등록, 프로젝트 수정, 주문 삭제.
3. 최종 와이어프레임에서 DB 열 구조가 반영된 화면은 어떤 화면이었어?
4. 고객사 요구사항 중 가장 애매하거나 정리하기 어려웠던 부분은 뭐였어?
5. ERD나 테이블 구조가 중간에 바뀐 적이 있어? 바뀌었다면 왜 바뀌었어?
6. 이 프로젝트를 개발자/기획자/AX 직무 중 어디에 더 강하게 붙이고 싶어?

## 아직 조심해야 할 표현

- "실제 회사에서 사용 중"이라고 말하려면 근거가 필요하다.
- "개발 100%"라고 말하기보다는 "SQLite 기반 CRUD SQL 작성과 물리적 설계에 기여"가 현재 확인된 표현이다.
- "고객사와 직접 개발 납품"이라고 말하기보다는 "실제 회사 요구사항 기반 제안/설계 프로젝트"가 더 안전하다.
