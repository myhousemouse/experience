# 로우코드 구현과 기술 의사결정

## 핵심 제약

- Flextudio의 FlexDB/FlexSQL 관련 가이드가 충분하지 않았다.
- 커스텀 API 호출과 데이터 저장 흐름에서 오류가 발생했다.
- 사진 데이터베이스, 좌표 반환, 지도 마커 렌더링 등에서 구현 난도가 높았다.

## 의사결정 1: 지도 중심에서 리스트 중심으로 조정

초기 목표는 지도 위에 제설 중/미완료/결빙 위험 상태를 색상이나 아이콘으로 표시하는 것이었다. 그러나 지도 API와 로우코드 툴 간 동적 마커 제어가 쉽지 않아, 사용자가 즉시 판단할 수 있는 `위험도 TOP 10 리스트` 중심으로 기능 전달 방식을 조정했다.

## 의사결정 2: Spring 서버 전송 대신 Google Sheets 연동

초기에는 시민 제보 데이터를 Spring 서버로 보내는 구조를 고려했다. 하지만 로우코드 앱에서 커스텀 API로 안정적으로 전송하는 과정이 불확실했다. 그래서 Google Sheets API를 대안 저장소로 사용해 제보 데이터를 먼저 안정적으로 적재하고 조회하는 방향을 택했다.

## 의사결정 3: RAG 서버 대신 OpenAI 직접 호출

초기에는 Python FastAPI와 벡터 DB를 붙인 RAG 서버를 고려했다. 최종적으로는 로우코드와 멀티 서버 연동 복잡성을 줄이기 위해 OpenAI API 직접 호출과 프롬프트 엔지니어링으로 빙판길 안전 챗봇을 구성했다.

## 구현 흐름

1. GPS 기반 현재 위치 수집
2. 네이버 지도 API 연동
3. 위도/경도 값을 주소로 변환
4. 위험 등급, 설명, 위치 정보를 제보 데이터로 구성
5. Google Sheets에 저장
6. 앱 화면에서 최신순/위험도순 리스트로 조회
7. 챗봇 화면에서 OpenAI API 응답 표시

## 의미

이 프로젝트의 핵심은 고도화된 기술을 모두 완성한 것이 아니라, 로우코드 툴의 목적에 맞게 구현 범위를 조정하고 작동 가능한 서비스를 만드는 것이다.
